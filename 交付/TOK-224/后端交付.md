## 一、结论摘要

服务端在简体中文界面实际显示的英文提示，几乎全部经由**一条路径**进入界面：
服务端 HTTP 响应的顶层 `error` 字符串 → 前端 `ui/src/api/client.ts` 把它原样抛成
`ApiError.message` → 各页面的错误横幅 / toast 原样渲染。

本轮为该路径建立了**按语言返回中文的机制**：

1. **语言解析**（`server/src/i18n/locale.ts`）：`X-Paperclip-Locale` 请求头
   （显式覆盖，前端语言切换器的接入点）→ `Accept-Language`（浏览器自动携带，
   按 RFC q 值协商）→ 默认 `en`。
2. **zh-CN 词表**（`server/src/i18n/zh-cn-messages.ts`）：120 条整串精确条目
   + 12 条锚定模板（数据原样保留，只译句子框架），术语完全沿用前端
   `ui/src/i18n/locales/zh-CN.json` 已确立的对照（issue→任务、agent→智能体、
   secret→机密、chat endpoint→聊天连接、company→公司、routine→例程、
   pipeline→流水线、case→案例、document→文档、workspace→工作区…）。
3. **单点翻译中间件**（`server/src/i18n/localize-error-responses.ts`）：在
   `app.ts` 注册于 body 解析器**之前**，包一层 `res.json`，只翻译顶层 `error`
   字符串字段。这一个包点覆盖全部错误出口：error-handler 的 HttpError / Zod
   「Validation error」/ 坏 JSON「Invalid JSON body」/ 崩溃兜底「Internal server
   error」、约 3,400 处 `HttpError` 助手调用、约 450 处路由内直接
   `res.status(...).json({ error: ... })` 写入、以及 `/api` 兜底 404。
   不改任何业务代码。

**默认路径不变**：不带语言头的请求（CLI、agent、webhook、curl）逐字节保持英文
响应。已用现有 28 条错误路径回归测试 + 线上探针双重核对（见 §四）。

## 五、前端适配契约（交经理整合协调，本席未改任何前端文件）

要让**界面语言切换器**（`localStorage["paperclip.locale"]`）也控制服务端提示，
只需在 `ui/src/api/client.ts` 的 `request()`（`applyObservabilityHeaders(headers);`
之后）加一行：

```ts
headers.set("X-Paperclip-Locale", <当前 i18next 语言，如 "zh-CN">);
```

- 服务端语义：`X-Paperclip-Locale` > `Accept-Language` > 默认英文；
  头值为不支持语言（如未建词表的 38 个占位语言）时自动回落到 Accept-Language，
  不会把界面切到英文的用户误送英文以外的东西。
- 词表/字符串**不需要**前端维护：前端只传语言码，译文全在服务端
  `server/src/i18n/zh-cn-messages.ts`。
- 不加这行也不影响 zh 浏览器用户（Accept-Language 自动生效）；
  差别仅在「浏览器语言与界面切换器不一致」的用户。

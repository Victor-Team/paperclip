## 怎么用这份单子

- 共 **12 条**验收条件，每条**独立判定**「通过 / 不通过」，不打分、不折中。
- **AC-01 ~ AC-05 是红线条，任一条不通过，整步判不通过**，不看后面的条目。
- 判定只认**证据**：命令输出、文件内容、截图。**报告里写「已完成」但拿不出对应证据的，一律判不通过。**
- 证据应在 `/home/yuanjian/dev/ANC/交付/第1步/` 下：`构建记录.md` 与 `截图/`。

### 🔴 验收开始前：先自己把新实例重起一次

执行方是在自己的运行里启动服务的，**那个进程在你验收时早已结束**（任务书步骤 7 也要求关掉）。所以甲、乙两组里凡是写「给定新实例已启动」的条目，都指**你按 `构建记录.md` 自己重起的那一次**，不是执行方当时那一次。

做法：照 `构建记录.md` 从头跑一遍启动步骤（含清环境变量、导出 `PAPERCLIP_HOME` / `PAPERCLIP_INSTANCE_ID` / `PORT`）。

- **起不来，或文档里缺步骤、得回头问执行者才能起来** → 直接判 **AC-11 不通过**，整单退回，不必再往下测。
- 这一步同时就是 AC-11「别人照着能重跑」的实测，不是额外负担。

另：**在重起新实例之前**，先从正式平台界面上记下当前公司清单（AC-04 的基线要用）。

## 甲、红线条（隔离，任一条不过即整步不过）

### AC-01 正式平台的 HTTP 端口没被抢

**给定** 新实例已启动，**当** 验收席执行 `ss -ltn | grep -E ':(3100|3200)'`，**则** 必须同时看到 `127.0.0.1:3100` 与 `127.0.0.1:3200` 两个监听项，且 `3200` 不是正式平台进程。

- 通过：两个端口各有独立监听。
- 不通过：新实例监听在 3100；或 3100 消失／被替换。

### AC-02 数据库端口没被抢，也没有连到正式库

**给定** 新实例已启动，**当** 检查 `/home/yuanjian/.paperclip-anc/instances/anc/config.json` 中 `database.embeddedPostgresPort` 的值，**则** 必须是 `54339`；且 `ss -ltn` 中 `54329`（正式）与 `54339`（新）同时存在、互不相同。

- 不通过：该字段仍是 `54329` 或缺失；或构建记录显示**曾经用 54329 起过一次**（哪怕后来改了）。
- 备注：此项对应任务书 R3，是本步最易被忽略的失败点，**必须逐字核对 config.json 的实际内容，不接受口头声明**。

### AC-03 数据目录完全独立

**给定** 新实例已完成引导，**当** 执行 `ls /home/yuanjian/.paperclip-anc/instances/anc/`，**则** 该目录存在且含有配置与数据；并且新实例的任何配置、日志、数据库文件**都不落在** `/home/yuanjian/.paperclip/` 下。

- 不通过：新实例数据写进了 `~/.paperclip/instances/default/` 或其任何子目录。

**追加检查（可机验，v1.1 补正；不替代上面的原判据）**：新实例 `/home/yuanjian/.paperclip-anc/instances/anc/config.json` 必须**实际含有**下列五个字段，且每个字段的取值都以 `/home/yuanjian/.paperclip-anc/instances/anc/` 为前缀（与任务书 v1.1 步骤 4a 硬性取值表同级）：

| 字段 | 本单规定值 |
|---|---|
| `database.embeddedPostgresDataDir` | `/home/yuanjian/.paperclip-anc/instances/anc/db` |
| `database.backup.dir` | `/home/yuanjian/.paperclip-anc/instances/anc/data/backups` |
| `logging.logDir` | `/home/yuanjian/.paperclip-anc/instances/anc/logs` |
| `storage.localDisk.baseDir` | `/home/yuanjian/.paperclip-anc/instances/anc/data/storage` |
| `secrets.localEncrypted.keyFilePath` | `/home/yuanjian/.paperclip-anc/instances/anc/secrets/master.key` |

机验（字段存在且取值均在规定目录下即通过；缺字段、空值、或取值落在 `~/.paperclip/` 下即不通过）：

```sh
python3 - <<'PY'
import json, sys
p = "/home/yuanjian/.paperclip-anc/instances/anc/config.json"
prefix = "/home/yuanjian/.paperclip-anc/instances/anc/"
cfg = json.load(open(p))
pairs = {
    "database.embeddedPostgresDataDir": (cfg.get("database") or {}).get("embeddedPostgresDataDir"),
    "database.backup.dir": ((cfg.get("database") or {}).get("backup") or {}).get("dir"),
    "logging.logDir": (cfg.get("logging") or {}).get("logDir"),
    "storage.localDisk.baseDir": ((cfg.get("storage") or {}).get("localDisk") or {}).get("baseDir"),
    "secrets.localEncrypted.keyFilePath": ((cfg.get("secrets") or {}).get("localEncrypted") or {}).get("keyFilePath"),
}
ok = True
for k, v in pairs.items():
    print(f"{k}={v!r}")
    if not (isinstance(v, str) and v.startswith(prefix)):
        ok = False
print("PASS" if ok else "FAIL")
sys.exit(0 if ok else 1)
PY
```

- 不通过（追加）：任一字段缺失；或任一取值不在 `/home/yuanjian/.paperclip-anc/instances/anc/` 下。

### AC-04 阴性对照——正式平台数据没被污染

**给定** 新实例里已建好测试公司，**当** 查询正式平台 `http://127.0.0.1:3100` 的公司清单，**则** 清单里**不出现** `ANC 测试公司`，且正式平台的公司数量与本步开始前一致。

- 这是判定隔离是否真的成立的**决定性条目**——「新实例能建公司」本身不足以证明隔离，两边都查才算数。
- **主判据**（必须满足）：正式平台的公司清单里**不出现** `ANC 测试公司`。出现即判不通过，并立即上报。
- **辅判据**（尽力取证）：公司数量与本步开始前一致。取基线的方式见下方说明；确实取不到基线时，本条**仍按主判据判定**，但需在验收结论里注明「数量对照缺基线」。
- 📌 取证说明（已实测）：席位手上的 API 凭证**读不到**正式实例的公司清单——`GET http://127.0.0.1:3100/api/companies` 返回 `{"error":"Board access required"}`。因此基线只能由有 board 权限的一方从正式平台界面上看一眼并记下来，**且必须在新实例启动之前记**。任务书步骤 0 已把这件事列为执行方的前置动作。

### AC-05 没有越界改动

**给定** 工作目录 `/home/yuanjian/dev/ANC`，**当** 执行 `git status --short` 与 `git log --oneline -3`，**则**：

- 已跟踪文件**零改动**（`LICENSE`、界面文案、任何源码、`pnpm-lock.yaml`、`package.json`、`.gitignore` 均未修改）；
- 未跟踪项中，`交付/` 是预期内的；**出现其他未跟踪项时**，须能在 `构建记录.md` 里找到来源说明（`dist/`、`node_modules/`、`.env` 已被仓库 `.gitignore` 覆盖，正常不会冒出来）；
- **没有任何新提交**、没有 `git push` 记录（`git log origin/master..HEAD` 为空）。

不通过：出现任何已跟踪文件的改动；或有本地提交、推送痕迹；或冒出来历不明的未跟踪文件。

## 乙、功能条

### AC-06 代码是取回来的，不是重建的

**给定** 工作目录，**当** 执行 `git log -1 --format=%H` 与 `git remote -v`，**则** HEAD 落在 `origin/master` 线上（基线 `bd51f157e9aade37f2f4602eda238fe51405a0c2` 或其后继），且 `origin` 仍指向 `https://github.com/Victor-Team/paperclip`。

不通过：`.git` 被重新初始化；或代码是从别处 clone 后搬来的（表现为无 `origin` 追踪关系或远端不符）。

### AC-07 实际主分支名已写明

**给定** 交付说明，**当** 查看构建记录，**则** 其中明确写出了远端实际使用的主分支名。

- 需求规格席已实测远端**只有 `master` 一个分支**；构建记录写「实际为 master，与预期一致」即通过。
- 不通过：完全没提分支名。

### AC-08 构建产物真的产生了

**给定** 已执行 `pnpm build`，**当** 查看构建记录，**则** 该步骤退出码为 `0`，且有可查的输出摘录。

不通过：退出码非 0 而报告称成功；或只有结论没有输出。

### AC-09 首页能打开

**给定** 新实例已启动，**当** 在浏览器访问 `http://127.0.0.1:3200`，**则** 首页正常渲染（非报错页、非空白页），且 `curl -s http://127.0.0.1:3200/api/health` 返回 `{"status":"ok"}`。

证据：首页截图 + health 输出。

### AC-10 能在新实例里新建一家测试公司

**给定** 新实例首页已打开，**当** 新建名为 `ANC 测试公司` 的公司，**则** 创建成功并能在新实例中看到它。

证据：创建后的截图。

⚠️ **判据提醒**：新取回的是**空白全新系统**，里面**不会有**我们现在这家公司和任何席位。**「能看到现有公司和席位」是错误判据，不得以此判不通过。** 反过来，若新实例里**竟然**出现了我们现有的公司或席位，说明它连上了正式实例的数据——**直接判 AC-04 不通过**。

## 附录 · 关于「能启动」指哪个入口（v1.2 新增；自第 2 步起生效）

> 本节是入口定义的**唯一正文**。任务书 §4c 只写执行后果并指向这里，不另写一份定义。
> 第 1 步验收席 / 整机放行席复审：**忽略本节**，继续按页眉以上正文 + v1.1 + TOK-161 裁定判。

### 1. 本项目语境下的两个文档化入口

| 名称 | 命令 | 来源 | 在本项目里的身份 |
|---|---|---|---|
| **默认生产入口** | `pnpm paperclipai run` | 仓库 `docs/deploy/local-development.md` §One-Command Bootstrap；任务书 §4c 推荐项 | **R1「默认整机验收」在本项目里的对象。** 走托管 CLI：config 缺失时自动 onboard、跑 `paperclipai doctor`（repair 开启）、检查通过后起服务。 |
| **文档化开发入口** | `pnpm dev` 或其无监视变体 `pnpm dev:once` | 仓库 `docs/deploy/local-development.md` §Start Dev Server；`package.json` scripts；`doc/DEVELOPING.md` | 仓库自己文档化的开发路径。`dev:once` 与 `dev` 是同一条 `scripts/dev-runner.ts` 装配，只是去掉文件监视与自动重启，**不是第三种入口**。 |

二者都载入同一份 server 源码，但**启动 Gate、生命周期与编排不同，不能据此判接线等价**。

### 2. 「默认生产入口」正面定义（不许下游再解释）

在 ANC 平台改造这条线上，**「默认生产入口」固定为下面这一组，一个字都不许改写成别的命令：**

```
工作目录：/home/yuanjian/dev/ANC
环境：先 unset 全部 PAPERCLIP_*，再只导出
  PAPERCLIP_HOME=/home/yuanjian/.paperclip-anc
  PAPERCLIP_INSTANCE_ID=anc
  PORT=3200
命令：pnpm paperclipai run
```

这就是跨项目规矩「默认整机验收」（R1）落在本项目里的对象。R1 的原文是：「一个功能不算 done，直到默认生产入口真跑一次、且断言该能力已激活。」

**R1 防的是用下面三类东西冒充「跑通了」：**

| 冒充类型 | 本项目落地 |
|---|---|
| 临时脚本 | 仓库 `package.json` / 部署文档未记载的启动包装、用完即删的一次性 shell |
| 特殊 flag | 任务书未授权、且该入口的仓库文档未记载的命令行开关或额外环境变量（任务书第四节规定的三个变量除外） |
| 一次性夹具 | 不能按构建记录重跑、只留结论的启动方式 |

**明确排除：** `pnpm dev` 与 `pnpm dev:once` 来源是仓库自己的 `docs/deploy/local-development.md`（及 `package.json` / `doc/DEVELOPING.md`），**不属于上面三类**，因此**不是冒充**。把开发入口当成「没走默认生产入口」是对的；把它当成「用临时脚本造假」是错的——第 1 步那次撞车，就是把这两句话混成了一句。

下游不得把「默认生产入口」重新解释成 `pnpm dev`、`pnpm dev:once`、带额外 flag 的变体、或任何临时脚本。

### 3. 一条 AC 说「给定新实例已启动」时，指哪个入口？

先看**本步是哪一种情形**，再读 AC。

| 情形 | 该按哪个入口判 |
|---|---|
| 本步零功能变更、只验「本机能不能把分叉跑起来」 | 任务书 §4c 授权的二选一：默认生产入口 **或** 文档化开发入口。选了哪个以构建记录为准；所选入口把实例拉起来，即满足「已启动」。 |
| 本步改了功能、要验该功能已激活 | **只认默认生产入口** `pnpm paperclipai run`。开发入口的证据只能作辅证，不能单独证明「该功能已激活」。 |
| 两个入口结论不一致时 | **必须分列填报**，不得合成一张「全过」表。零功能变更步：开发入口通过 → 本步「能启动」相关 AC 可通过；默认入口失败必须保留「默认入口未验证」标注，并立为下一步的一等前置（不得因本步通过而冲掉）。功能变更步：以默认生产入口为准；它失败则该功能未激活，本步不得判通过。 |

### 4. 从第 2 步起，AC-09 / AC-10 / AC-11 怎么读

AC-01～AC-12 原文一个字都没改。下面只约束**怎么读「已启动」**：

| AC | 从第 2 步起怎么读「已启动」 |
|---|---|
| **AC-09 首页能打开**、**AC-10 能新建测试公司**，以及所有写「给定新实例已启动」的条目（含 AC-01） | 按第 3 节的情形表。第 2 步起若本步改了功能，这些条目里的「已启动」= 默认生产入口已把 `127.0.0.1:3200` 拉起来。 |
| **AC-11 构建记录可被别人照着重跑** | 「照构建记录重起」的命令以记录里写明的为准。零功能变更步：记录写开发入口即按开发入口重起。功能变更步：记录必须写明默认生产入口 `pnpm paperclipai run` 的复现步骤；若只写了开发入口，本条在「别人照着能重跑本步要验的功能」这一层不通过。无论哪一步，只要默认生产入口没跑通，记录必须保留「默认入口未验证」——不得省略。 |
| **AC-03～AC-08、AC-12** | 不依赖入口选择（隔离路径、取代码、构建产物、耗时记录）。入口争议不影响这些条目的原判据。 |

## 一、这一步要解决的问题

**用户与场景**：公司要把自己在用的这套工作平台改造成中文自有版本（共五步）。在动任何一行代码之前，得先有一份**属于我们自己、能在本机独立构建并跑起来**的副本。第 1 步的使用者是开发部·软件架构席，场景是：拿到一个已挂好远端的空仓库目录，把代码取回来，装依赖、构建、启动，并且**绝不碰正在为全公司干活的那套正式平台**。

**这一步做完的标志**：本机上同时有两套平台在跑——正式那套（端口 3100）一切照旧、数据分毫未动；新的那套（端口 3200）是空白系统，能打开首页、能新建一家测试公司。

## 二、范围

本单**只做**下面四件事：

1. 把 `origin` 上的代码取回工作目录并切到主分支。
2. 按仓库自带文档装依赖、构建。
3. 用**本单规定的端口与数据目录**启动服务。
4. 记录构建耗时、失败步骤与原文报错，并写成一页可重跑的文档。

2. **不改任何代码逻辑**、不改配置文件的业务含义、不改 `LICENSE`（MIT，版权方 Paperclip AI，2025）与任何版权/许可声明。

## 四、🔴 隔离红线：端口与数据目录（本单规定，写死）

正式平台跑在本机，**它的数据是全公司的家底**。已实测确认它当前占用：

```
127.0.0.1:3100    正式平台 HTTP 服务
127.0.0.1:54329   正式平台的内嵌 PostgreSQL     ← 最容易被忽略的一条
```
（证据：本机 `ss -ltn` 输出；端口 54329 的来源见下方 R3）

新实例**必须**全部改用下面这组值，一个都不许沿用默认：

| 项 | 本单规定值 | 平台默认值（不许用） | 依据 |
|---|---|---|---|
| HTTP 端口 | **3200** | `3100` | R1 |
| 数据根目录 | **`/home/yuanjian/.paperclip-anc`** | `~/.paperclip` | R2 |
| 实例 id | **`anc`** | `default` | R2 |
| 内嵌 PostgreSQL 端口 | **54339** | `54329` | R3 |
| 绑定范围 | 保持默认 `loopback`（只监听 127.0.0.1） | — | R1 |

综合结果：新实例的全部数据落在 `/home/yuanjian/.paperclip-anc/instances/anc/` 下，与正式实例的 `/home/yuanjian/.paperclip/instances/default/` **没有任何路径交集**。

**依据（逐条可查）**

- **R1**：`docs/deploy/environment-variables.md` §Server Configuration —— `PORT` 默认 `3100`；`PAPERCLIP_BIND` 默认 `loopback`。
- **R2**：同上 —— `PAPERCLIP_HOME` 默认 `~/.paperclip`，`PAPERCLIP_INSTANCE_ID` 默认 `default`；解析逻辑见 `packages/shared/src/home-paths.ts:17,23`。`docs/deploy/local-development.md` §Data Locations 列出了 config / db / storage / secrets / logs 五类数据的落点，全都在这个目录下。
- **R3**：`packages/db/src/runtime-config.ts:223` —— `const port = config?.database?.embeddedPostgresPort ?? 54329;`。**这个端口没有环境变量可以覆盖，只能写在实例的 `config.json` 里**（字段路径 `database.embeddedPostgresPort`）。而 `cli/src/commands/onboard.ts:259` 在首次引导时把它**硬编码写成 `54329`**。

### 🔴 R3 为什么是本步最大的风险，必须专门处理

如果照默认走完引导就直接启动，新实例会去连 `127.0.0.1:54329`——**那正是正式平台的数据库**。后果是两种之一：轻则端口被占、启动失败；重则**连上正式库并往里写**，全公司数据受损。

所以本单要求：

> **在新实例第一次启动服务之前**，必须先让 `/home/yuanjian/.paperclip-anc/instances/anc/config.json` 里的 `database.embeddedPostgresPort` 变成 `54339`，并把改完后该文件的相关片段抄进构建记录作为证据。

`onboard` / `run` / `configure` 三个命令**都没有** `--db-port` 这类开关（已核对 `cli/src/index.ts` 的选项列表）。**唯一不可接受的做法是：先用 54329 起过一次再改。** 具体落地方式见步骤 4 与未决问题 U1。

### 🔴 另一条隐蔽风险：继承来的环境变量

执行本单的席位是在平台的 heartbeat 里干活的，进程环境里**天然带着正式实例的变量**（实测存在：`PAPERCLIP_API_URL=http://127.0.0.1:3100`、`PAPERCLIP_API_KEY`、`PAPERCLIP_LISTEN_PORT=3100`、`PAPERCLIP_LISTEN_HOST`、`PAPERCLIP_COMPANY_ID`、`PAPERCLIP_AGENT_ID`、`PAPERCLIP_TASK_ID`、`PAPERCLIP_RUN_ID` 等）。这些变量会被子进程原样继承。

要求：**启动新实例的那个 shell，必须先把所有 `PAPERCLIP_*` 变量清干净，再只导出本单规定的那几个。** 例如：

```sh
for v in $(env | grep -o '^PAPERCLIP_[A-Z_]*'); do unset "$v"; done
export PAPERCLIP_HOME=/home/yuanjian/.paperclip-anc
export PAPERCLIP_INSTANCE_ID=anc
export PORT=3200
env | grep -E '^(PAPERCLIP_|PORT=)' | sort   # ← 把这条的输出抄进构建记录
```

（`PAPERCLIP_LISTEN_PORT` 优先于 `PORT` 被读取，见 `packages/adapter-utils/src/server-utils.ts:3114`，所以它必须被清掉。）

### 步骤 4 · 起隔离实例

先按第四节把环境清干净并导出那三个变量。**隔离只靠这三个环境变量来实现，不要再加 `-d` 参数**——已核对 `cli/src/config/data-dir.ts:26-28`：`-d X` 的语义就是「把 `PAPERCLIP_HOME` 设成 X」，所以写 `-d .../instances/anc` 会得到 `.../instances/anc/instances/anc/` 这种双层嵌套路径，与本单第四节声明的数据目录不符，验收席会在不存在的路径上判不通过。用纯环境变量的形式正是 `docs/deploy/local-development.md` §Data Locations 给的形式。

#### 🔴 4a · 先解决「非交互」这道坎（**动手前必须先定，不许边试边闯**）

执行本单的席位跑在 heartbeat 的 Bash 里，**没有 TTY**。而 `onboard` 的分支是这样的（`cli/src/commands/onboard.ts`）：

| 走法 | 会发生什么 | 依据 |
|---|---|---|
| `onboard`（不加 `-y`） | 弹交互菜单 `Choose setup path`，无 TTY 下会卡住或报错 | `onboard.ts:527` |
| `onboard -y` | 用 quickstart 默认值建好配置，**并立即启动服务器** | `onboard.ts:499,770`：`shouldRunNow = ... (opts.run === true \|\| opts.yes === true)` |
| `configure -s database` | 同样是交互提示 | `cli/src/prompts/database.ts` |

而 quickstart 默认值里 `embeddedPostgresPort` 被**硬编码成 `54329`**（`onboard.ts:259`）。两条路合起来的后果是：`-y` 会带着 54329 直接起库，**这正是红线 R3 禁止的那一步**。

所以：**`onboard -y` 在本步被禁止使用**，`onboard`（交互）在本环境下也走不通。软件架构席必须先选定一条**非交互且不经过 54329** 的路径，写进构建记录再动手。已核实可用的候选（任选其一，也可另提）：

- **候选 A（推荐）· 先铺配置再启动**：手工在 `/home/yuanjian/.paperclip-anc/instances/anc/config.json` 写好配置（`embeddedPostgresPort: 54339`、`server.port: 3200`，**以及下面五个路径字段**），再跑 `pnpm paperclipai run`。依据：配置已存在时 `onboard` 直接返回 `Existing Paperclip setup is ready.` 不再引导（`onboard.ts:400,515`）；文档也写明 `run` 只在「config is missing」时才自动引导（`docs/deploy/local-development.md` §One-Command Bootstrap）。配置字段以 `cli/src/config/store.ts` 的 schema 与 `onboard.ts:255-290` 的默认值为准。
  - 顺带一提：`server.port` 的默认值取自 `Number(process.env.PORT) || 3100`（`onboard.ts:277`），所以按第四节导出 `PORT=3200` 后，这一项本来就会是 3200。

  ##### 🔴 候选 A 硬性取值：config.json 五个路径字段（本单规定，不许改；与第四节 R1/R2/R3 同级）

  `packages/shared/src/config-schema.ts` 里路径字段的默认值是**硬编码指向正式实例目录的字面量**，**不读 `PAPERCLIP_HOME`**（已核：第 33、45、66、91 行等）。`onboard` 不出事是因为它调 `resolveDefault*Dir()` 动态算路径；**手写 config.json 走的不是那条路**。漏写任一字段，对应那类数据就会落进 `~/.paperclip/instances/default/`——正是验收单 AC-03 判「不通过」的情形。

  下面五个字段必须显式写进 `/home/yuanjian/.paperclip-anc/instances/anc/config.json`，取值不许改、不许省略、不许沿用 `~/.paperclip/instances/default/...` 的 schema 默认值：

  |---|---|---|
  | `database.embeddedPostgresDataDir` | `/home/yuanjian/.paperclip-anc/instances/anc/db` | 新实例的**库**落进正式实例目录 |
  | `database.backup.dir` | `/home/yuanjian/.paperclip-anc/instances/anc/data/backups` | **备份**写进正式实例目录 |
  | `logging.logDir` | `/home/yuanjian/.paperclip-anc/instances/anc/logs` | **日志**写进正式实例目录 |
  | `storage.localDisk.baseDir` | `/home/yuanjian/.paperclip-anc/instances/anc/data/storage` | **附件**写进正式实例目录 |
  | `secrets.localEncrypted.keyFilePath` | `/home/yuanjian/.paperclip-anc/instances/anc/secrets/master.key` | **密钥**写进正式实例目录 |

  （路径形态与 `packages/shared/src/home-paths.ts` 在 `PAPERCLIP_HOME=/home/yuanjian/.paperclip-anc` + `PAPERCLIP_INSTANCE_ID=anc` 下算出的结果一致。明细只读引用 `构建记录.md` §4-A ~ §4-E。）
- **候选 B · 用平台自带的隔离实例机制**：`paperclipai worktree:make <名字> --seed-mode minimal --db-port 54339`。这是仓库文档专门为「安全的并行本地实验」推荐的做法（`docs/deploy/local-development.md` §Safe Worktree Bootstrap），且**它带 `--db-port` 开关**（`cli/src/commands/worktree.ts:4455`）。⚠️ 代价：它会另建一份 checkout 与分支，与本单「就在 `/home/yuanjian/dev/ANC` 里干活、不新建分支」的约定有冲突，**选它之前必须先上报确认**。

#### 4b · 启动前的最后一道自查（**必须有输出证据**）

在服务器第一次启动**之前**：


### 0. 缺陷（结构性，在我们自己的分叉里）

实例级判断「这个实例装过托管 CLI 吗」混进了一条**用户级**路径：

```
cli/src/install-store.ts（resolveInstallStorePaths）
    manifestPath / markerPath / currentPath  →  由 cliRoot 派生（跟随 PAPERCLIP_HOME）
    shimPath: path.join(homeDir, ".local", "bin", "paperclipai")   ← 跟随 $HOME

cli/src/checks/managed-install-check.ts（hasManagedArtifacts）
    [manifestPath, markerPath, currentPath, shimPath].some(fs.existsSync)
```

后果：**只要这台机器上正式实例装过 CLI，就再也无法用 `paperclipai run` 起任何隔离实例。** 本机 `/home/yuanjian/.local/bin/paperclipai`（202 字节，2026-08-31）正是那个 shim，它 exec 的是正式实例的托管安装。

整机放行席已实测：隔离实例上 `pnpm paperclipai run` 在 doctor 阶段以退出码 `1` 拒绝启动，3200 / 54339 均未监听。该事实由 TOK-161 裁定确认保留，不因第 1 步放行而被推翻。执行席的因果实验与修复边界见 `构建记录.md` §4-8 ⑤（只读引用，本规格不改那份文件）。

### 0.1 修复边界：二选一（默认乙；升甲必须满足判据）

| 方案 | 改什么 | 语义 |
|---|---|---|
| **甲** | `shimPath` 改由 `PAPERCLIP_HOME` 派生 | 让 shim 也变成实例级路径，与 manifest / marker / current 一致。 |
| **乙（默认）** | `hasManagedArtifacts()` **不把 shim 计入** store 存在性 | shim 是用户级单例，本就不是 store 的组成部分；本函数问的是「这个实例的托管 store 在不在」。 |

**本规格默认选乙。** 理由：缺陷的根因是「实例级问题混进用户级路径」，乙是对准根因的最小改动；甲会改变正式实例 CLI 的落点与 PATH 解析，触面更大。

第 2 步执行席开工第 0 项时确认一次。**升甲的判据（满足任一条即可升，必须把证据写进第 2 步构建记录再改）：**

1. 乙已经合入并在隔离实例上实测，`pnpm paperclipai run` 仍因 shim 指向正式实例托管安装而起不来；
2. 实测证明隔离实例必须有自己的可执行 shim，且不改 `shimPath` 就无法让默认入口在 `PAPERCLIP_HOME` 下工作。

禁止：

- 第 0 项未完成就开始第 2 步的功能改动；
- 把本项写成可选项、顺带项、建议项；
- 两条一起改，除非乙已按上面判据证明不够、且甲的必要证据已落盘；
- 覆盖、删除或重写 `/home/yuanjian/.local/bin/paperclipai`（第三节第 7 条：那是正式实例在用的二进制）；

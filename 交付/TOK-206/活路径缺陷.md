# TOK-206 · 恢复路径活路径缺陷

核查时间：2026-09-23（America/Los_Angeles）
规则版本：`blocked-no-live-path-v1`

## 项 1 · 已实现：恢复出口不再制造无自动唤醒路径

实现位于 `server/src/services/recovery/service.ts`：

- `ensureStrandedLivenessRetry` 先在同一事务中持久化 wake 请求和 `heartbeat_runs.status='scheduled_retry'`，并把 recovery action 标记为 `system` 的 `scheduled_retry`；
- `escalateStrandedAssignedIssue` 在无未完成 blocker、无既存 monitor 时，只有上述重试已落盘才把源单保持为 `in_progress`；它清空旧的 `unblockDescriptor`，不再把 board descriptor 或 recovery action 当作活路径；
- 若已有真实 blocker 或未来 monitor，原 `blocked` 路径保留。

最终定位：`recovery/service.ts:2700-2716` 只将同公司、实际已持久化的源 run
作为 `retryOfRunId`；`recovery/service.ts:2718-2817` 与
`recovery/service.ts:2820-2905` 分别持久化 quota 与 stranded scheduled retry。
`recovery/service.ts:4048-4069` 只在 retry 已落盘后保持 `in_progress`。
这保留了 retry-now 所需的真实 lineage，同时不为已经清理或测试构造的 source
run 写出悬空外键。

`server/src/services/execution-recovery-resolution.ts` 的另一条出口原先会把
`resolved + automaticRecovery.replay='blocked'` 长期留在
`executionBlockerPredicate` 中：普通 wake 仍被拦截，但已没有可投递的恢复。
现改为只识别系统写入的
`policy='preserve_without_replay_v1' + actionOutcome='unknown' + runId` 记录，
创建稳定键 `execution-recovery-only:<actionId>` 的一次性 wake。它不重放旧
provider 会话或旧工具调用；`server/src/services/heartbeat.ts` 只接受精确的
系统来源、action ID、源 run、强制新会话和匹配 idempotency key。入队时将源单
恢复为 `in_progress`，并在同一事务把该记录标为
`recovery_only_delivered`，因此后续普通 wake 不再被无限 defer。
最终定位：`execution-recovery-resolution.ts:197-329` 识别、投递及审计该
一次性 wake；`heartbeat.ts:26130-26152` 识别类别，
`heartbeat.ts:26922-27070` 验证系统来源、action/run/idempotency，
`heartbeat.ts:27913-28068` 原子恢复源单并把 hold 交付完成。

类形测试：`heartbeat-process-recovery.test.ts` 的 `keeps stranded in-progress work schedulable after a productive continuation retry was already used` 覆盖“任何重复 continuation 的无路径升级”：断言 `in_progress`、无 descriptor、`ownerType=system` 和一条 `stranded_liveness_recovery` scheduled retry。变异证据：临时删除此守卫后，该测试红（实际：期望 `in_progress`，收到 `blocked`）；随即恢复守卫，测试转绿。

`issue-recovery-actions.test.ts` 的
`delivers a resolved automatic no-replay hold through one fresh recovery-only wake`
覆盖 resolved no-replay 的并发 sweep：只生成一条 wake、其 run 绑定旧 run 且
`forceFreshSession=true`，并在交付后确认 `getExecutionBlocker(...) === null`。
变异证据：临时去掉该专用 wake 对 execution blocker 的豁免后，测试红（实际：
期望 1 条 wake，收到 0）；随即恢复。

本轮补齐两条回归：

- `issue-scheduled-retry-routes.test.ts:309-333` 分别证明
  `provider_quota_recovery` 与 `stranded_liveness_recovery` 都以真实
  `retryOfRunId` 被 `POST /issues/:id/scheduled-retry/retry-now` 找到并提升，
  不会返回 `no_scheduled_retry`；
- `issue-recovery-actions.test.ts:1898-1977` 构造 action/run/idempotency 都
  合法、但 `requestedByActorType='agent'` 的专用 wake，断言其被跳过且 hold
  保留。变异时将 `heartbeat.ts` 的 system guard 反转，该测试红（实际：期望
  `null`，收到 queued run）；随后恢复守卫。

## 项 3 · 死单判定与当刻核查

判定规则：`status='blocked'` 且 `blockedBy=[]`、`unblockDescriptor=null`、`monitorNextCheckAt=null` 且无 scheduled retry 时为**疑似死单，未穷尽核实**；需再核 pending interaction、queued wake、live run，皆无才可写“确认无自动唤醒路径”。

```sh
PAPERCLIP_API_BASE="${PAPERCLIP_API_URL%/}"; PAPERCLIP_API_BASE="${PAPERCLIP_API_BASE%/api}"
curl -sS -H "Authorization: Bearer $PAPERCLIP_API_KEY" "$PAPERCLIP_API_BASE/api/companies/$PAPERCLIP_COMPANY_ID/issues?status=blocked&includeBlockedBy=true" | jq '[.[] | select(((.blockedBy // []) | length) == 0 and .unblockDescriptor == null and .monitorNextCheckAt == null and .scheduledRetry == null) | {id,identifier,title,status}]'
```

当刻 HTTP `200`，候选：TOK-199、TOK-201、TOK-204；结论仅为“疑似死单 3，未穷尽核实”。

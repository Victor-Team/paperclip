## 一、根因（实查，非推断）

本机已安装外部适配器 `antigravity_local`：
`/home/yuanjian/.paperclip/external-adapters/node_modules/@weslleycapelari/adapter-antigravity-local`

`dist/server/execute.js` 第 306–330 行（实读）：

```js
const failed = (proc.exitCode ?? 0) !== 0;
...
return {
  exitCode: proc.exitCode,
  errorMessage: failed ? fallbackErrorMessage : null,
  resultJson: agyJson ? { raw: rawStdout, parsed: agyJson } : { raw: rawStdout },
  summary: failed ? "" : agyText,
};
```

即：**CLI 退出码为 0 时，适配器一律上报 `errorMessage: null`**，哪怕结构化终响应
`resultJson.parsed.status === "ERROR"`（429 RESOURCE_EXHAUSTED）。
而 `server/src/services/heartbeat.ts` 的结局判定此前只看 `exitCode`/`errorMessage`/`signal`，
于是把 429 失败轮次落库成 `succeeded`——这正是 TOK-179 的 `726f0a95` / `802c597a` 两次运行。

被标成功之后，provider-quota 恢复通道完全不会被触发，任务转入
`successful_run_handoff_required` → `successful_run_handoff_escalated`，只留一句
「board decision is required」的散文，任务树停死。

附带发现（同一根因的第二层）：即使运行被正确标为 `failed`，
`recovery/service.ts` 的 `PROVIDER_QUOTA_ERROR_RE` 也**匹配不上** Gemini CLI 系的 429 措辞
（`RESOURCE_EXHAUSTED`、`quota reached`、`exceeded the weekly usage quota`），
仍会退化成普通 adapter 失败、丢掉配额退避。两层都堵上才算修完。

## 五、与任务书的偏离（须复核人裁定）

原单「期望」三条，本轮**只完成第 1 条的 ERROR 半边**。逐条说明：

### 期望 1（ERROR / 空响应不得标 succeeded）—— ERROR 已修；**空响应故意不改**

反驳理由：Paperclip **已经**有一条一等的空响应通道，把它改成 `failed` 是倒退。

- `server/src/services/run-liveness.ts:345,367` 把「成功但无有效输出」判为 `empty_response` liveness；
- `server/src/services/recovery/run-liveness-continuations.ts:11` 把 `empty_response` 列为
  **可续跑状态**，默认给 2 次有界续跑（`DEFAULT_MAX_LIVENESS_CONTINUATION_ATTEMPTS`），
  耗尽后产出明确的「交人处置」评论。

若把 `SUCCESS + 空正文` 判成 `failed`，这条现成通道会被整条绕开，
换来一个泛化的 adapter 失败，且要在 errorCode 命名空间里新造 `empty_response` 一词
（该词现在只属于 liveness 命名空间，两处同名不同义会长期误导）。

TOK-179 的证据也支持这一判断：`85a8962a`（SUCCESS + 空）当时**确实**走到了
`successful_run_handoff_required`——那条路是通的。真正停死任务树的是 `726f0a95` / `802c597a`
两次 **ERROR 429 被标成功**，也就是本轮修掉的那一半。

⚠️ 这是我单方判断，未经复核。若复核人认为仍应按字面把空响应也标失败，请驳回本条，我按裁定改。

### 期望 2（恢复失败后建一等 waiting path）—— 未实现

本轮修复把 429 挡在了进入 missing-disposition 升级**之前**（改走 provider_quota 退避，
那本身就是一等等待路径），因此 TOK-179 的具体复现路径已断。
但「`buildSuccessfulRunHandoffExhaustedNotice` 升级后只留散文、无 pending interaction、
无 named unblock owner」这个**纵深缺陷仍然存在**（`recovery/successful-run-handoff.ts:199-249`，
`recoveryOwner` 为空时只写 `"Board decision required"` 字面量）。需要单独派单。

## 一、改了什么

### 主缺陷

`server/src/services/recovery/successful-run-handoff.ts` 的 `buildSuccessfulRunHandoffExhaustedNotice()` 在 `recoveryOwner` 为空时只写一行散文 `"Board decision required"`——不建 interaction、不落 named unblock owner。missing-disposition 恢复耗尽后任务树没有任何一等存活路径（TOK-179 `802c597a` 之后董事会问「什么情况？」无人应答的根因）。

### 修复（方案选择与理由）

**选择：在一等 interaction 通道上落 `ask_user_questions` 卡片**（备选是 named unblock owner + 恢复动作）。理由：

1. 到达这条升级路径的前提就是 `recoveryOwner` 为空（recovery action 已把 ownerType 交给 board、`returnOwnerAgentId` 只用于配额等待监视），**不存在**可指名的 agent 恢复 owner——能且只能等董事会处置；
2. 平台已有完整的 interaction 生命周期（pending → accepted/rejected/expired、幂等键去重、`continuationPolicy: wake_assignee` 在接受与拒绝时都唤醒），接受后唤醒的正是原 assignee（escalation 全程保留 source assignee），恰好就是「让原席位落实董事会选择」这条链；
3. named-owner 方案在这条路径上无 owner 可写，强写只会造出第二个无响应死角。

### 三种结局（`ensureSuccessfulRunHandoffBoardWaitingPath`，successful-run-handoff.ts:337）

| 场景 | 行为 | 一等对象 |
|---|---|---|
| 有 named recovery owner | 不建卡，返回 `{kind:"recovery_owner"}`，owner 即 wakeable 路径 | recovery action 行（已有） |
| 无 owner（本缺陷场景） | 建 `ask_user_questions` interaction，落库 `issue_thread_interactions` 一行 | interaction 行 |
| 创建失败 | 有界重试（默认 2 次）→ 返回 `{kind:"unavailable", failureReason}` → notice metadata 记 `unavailable:<原因>`，issue 保持 blocked | notice metadata 行（可查） |

### 面向董事会的卡片文案（中文红线）

`buildSuccessfulRunHandoffBoardDispositionRequest()` 生成的卡片：标题、摘要、问题、五个选项全部中文；摘要含「答了会发生什么／不答会怎样／没定的是哪一处／权限变更：不涉及」；证据给出绝对路径。选项：

1. `mark_done_or_cancelled` —— 已完成或就此取消，结掉这张单
2. `send_for_review_or_ask_for_input` —— 送去复核，指定复核人
3. `mark_blocked` —— 原样保持阻塞（说明需写明解阻人与动作）
4. `delegate_or_continue_from_checkpoint` —— 让原席位接着做
5. `other`（freeText）—— 董事会自行说明

关键参数：`continuationPolicy: "wake_assignee"`（答了就唤醒原席位执行）；`supersedeOnUserComment: false`（董事会追问评论不注销这张卡——这张卡是本 issue 唯一的一等存活路径，被评论作废就回到死角）；幂等键 `successful_run_handoff_board_disposition:<issueId>:<sourceRunId>:<recoveryActionId>`，按来源运行隔离，两条入口不塌缩成一张卡，重放不重复建卡。

### 接线点

`server/src/services/recovery/service.ts:3833`——`escalateStrandedAssignedIssue` 在 `recoveryCause === "successful_run_missing_state"` 且有 handoff evidence 时，**建 notice 之前**先 `ensureSuccessfulRunHandoffBoardWaitingPath(...)`，把返回的 `waitingPath` 传给 `buildSuccessfulRunHandoffExhaustedNotice`；notice 的 Recovery section 新增 `Board waiting path` 行，值为 `issue_thread_interaction:<interactionId>` / `recovery_owner:<agentId>` / `unavailable:<reason>`。

### 两条入口为何都在这里收口

- **429 配额路径**：TOK-185 已让结构化 ERROR/空响应判 `failed`，`classifyAdapterFailureForRecovery` 归 `provider_quota`，纠正运行耗尽后经 `FINISH_SUCCESSFUL_RUN_HANDOFF_REASON` 唤醒链走到本升级。
- **`empty_response` 续跑路径**：`run-liveness.ts:345,367` 判 `empty_response`，`run-liveness-continuations.ts` 默认 2 次有界续跑，耗尽后判 `successful_run_handoff_required`（TOK-179 `85a8962a`：SUCCESS + 空），其纠正 handoff 运行的 contextSnapshot 带同一组 `wakeReason/handoffReason/handoffAttempt` 字段，`successfulRunHandoffRecoveryEvidence()`（service.ts:744）按这组字段识别——两条入口汇入同一个 `escalateStrandedAssignedIssue` 调用，waiting path 在汇合点创建，天然覆盖两条入口。

## 五、R6 三问

1. **默认生产路径调用了吗？** 是。`escalateStrandedAssignedIssue` 是恢复耗尽的唯一生产汇合点（heartbeat.ts handoff 链与 run-liveness 续跑链都到达它），waiting path 在其内部无条件创建（仅 recoveryOwner 非空这一业务前提会跳过建卡，那是正确语义而非 flag），不依赖任何 feature flag / env。集成测试即以该生产函数为入口。
2. **结构化输出真填充还是占位空？** 真填充。`waitingPath` 由真实 create 的返回值填充（`issueThreadInteractionService(db).create(...)` 落库返回的行含真实 uuid），写入 notice metadata `Board waiting path` 行并随系统评论持久化；失败时写入真实错误原文。消费者：issue 线程 UI 的 system_notice 渲染 + 任何按 metadata 检索的证据链。
3. **不变量是代码强制还是只在文档？** 代码强制：无 owner 时唯一出路是 create 成功（返回 id 才算 `board_interaction`），create 抛错走有界重试 → `unavailable` 标记，不存在「既没卡也没标记」的分支；幂等键防重由 DB 层 `issue_thread_interactions.idempotency_key` 语义强制。

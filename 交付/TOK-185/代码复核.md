1. **gemini_local process（#5）**：`status`/`is_error` 直接来自 Gemini CLI 自己的 `result` 事件，语义正是"本轮 agent 回合是否失败"，与新守卫的设计意图完全一致。已知一例。
2. **claude_local process（#6）**：`is_error` 来自 Claude CLI stream-json 的 `result` 事件，语义同上。且验证了 `execute.ts:1124` 的 `parsedIsError` 与最终 `resultJson.is_error` **同源**（都来自 `parsed.is_error`），`execute.ts:1125` 的 `failed` 判定本身已把 `parsedIsError===true` 纳入失败条件（`const failed = !parsedSucceeded && ((proc.exitCode ?? 0) !== 0 || parsedIsError)`），因此凡 `is_error===true` 必然伴随非空 `errorMessage`。heartbeat.ts 的 exit-code 分支要求 `!adapterResult.errorMessage`，这种场景本就走不到 succeeded 分支——新守卫是重复判断，不产生额外误判。
3. **acpx-engine（#9）**：`resultJson.status` 的三个取值（"completed"/"failed"/"cancelled"）来自 `terminal.status`，是 ACP 协议 turn 的终止状态，**不是** Gemini CLI JSON 契约的 SUCCESS/ERROR。核实关键不变量：`execute.ts:4971` 的 `exitCode: turnSucceeded ? 0 : 1` 与 `execute.ts:4973` 的 `errorMessage`（非成功时非空，`resultErrorMessage(terminal)`）**都**与 `turnSucceeded`/`terminal.status` 同源派生——是**双重独立门**（exitCode 非 0 + errorMessage 非空双双拦截），不是单点耦合。只要 `status!=="completed"`，`exitCode` 必为 1，新守卫所在的 `(exitCode===0 && !errorMessage && ...)` 分支根本进不去，不会被触发。`adapter-final-response.test.ts:74-84`（"ignores unrelated status vocabularies such as turn results"，含 `status: "cancelled"` 用例）显示实现者已经意识到 acpx 的词汇表并显式排除。**结论：无误判风险，但语义耦合是隐式的（守卫本身不知道 acpx 的存在，靠字段同源这一不成文约定维持安全）**——列为建议项，见问题清单 B1。
4. **antigravity_local（#10，本机已安装外部插件，一手源码核验）**：确认 `resultJson = agyJson ? {raw, parsed: agyJson} : {raw}`（顶层只有 `raw`/`parsed`，无并列的顶层 `is_error`/`status`）。且确认该插件自身的 `failed` 判定**只看 `exitCode`**（`execute.js:276`：`const failed = (proc.exitCode ?? 0) !== 0`），完全不检查 `agyJson.status`/`is_error`——**这正是 TOK-185 要修的原始 bug 现场**：该插件在 429/ERROR 场景下会 `exitCode=0`、`errorMessage=null`，把 ERROR 静默丢在 `resultJson.parsed` 里。这与 `heartbeat-retry-scheduling.test.ts` 新增测试的注释"Mirrors the installed antigravity_local plugin"描述一致，已用一手源码而非自述验证。
5. **cursor_cloud process（#12，新增，一手源码核验）**：`execute.ts:580` `const isError = result.status !== "finished"` 与 `execute.ts:582` `exitCode: isError ? 1 : 0` **同源**——两者都直接派生自同一个 `result.status` 变量。因此新守卫能进入的唯一场景（`exitCode===0`）必然对应 `result.status==="finished"`，大写化后是 `"FINISHED"`，不等于 `"ERROR"`/`"FAILED"`，不会被新守卫命中。**结论：同源双写，无误判风险**（与 #6 claude_local 的"重复判断不产生额外误判"同构）。
6. **hermes_gateway process（#15，新增，一手源码核验）**：`execute.ts:654-658` 的 `terminalResultCode(status)` 函数把 `input.terminal.status==="completed"` 映射为 `exitCode:0`，其余映射为 `exitCode:1`；而 `resultJson.status` 直接写入同一个 `input.terminal.status` 值（`execute.ts:701`）。同样是单一变量同时驱动 `exitCode` 与 `resultJson.status`。`exitCode===0` 只可能对应 `status==="completed"`，大写化 `"COMPLETED"` 不等于 `"ERROR"`/`"FAILED"`，不会被命中。**结论：同源双写，无误判风险**。
7. **openclaw_gateway process（#17，新增，一手源码核验，含追踪 `latestResultPayload` 的全部赋值点）**：`execute.ts:1181` 初始化 `let latestResultPayload: unknown = null`，只有两处赋值——`execute.ts:1328` `latestResultPayload = acceptedPayload`（`agent` RPC 的响应，紧随其后即计算 `acceptedStatus`）与 `execute.ts:1359` `latestResultPayload = waitPayload`（仅当 `acceptedStatus !== "ok"` 时才会调用 `agent.wait` 并执行到这里）。到达 `exitCode:0` 的成功返回（`execute.ts:1439`）之前，代码路径只有两条：① `acceptedStatus==="ok"` 时跳过 `agent.wait`，直接把 `acceptedPayload`（`status==="ok"`）当作最终结果；② `acceptedStatus!=="ok"` 时进入 `agent.wait`，其后 `execute.ts:1369` 拦 `waitStatus==="timeout"`、`execute.ts:1382` 拦 `waitStatus==="error"`、`execute.ts:1393` 拦"非空且非 ok"的其它取值，全部提前 return failed；只有 `waitStatus==="ok"` 或**空字符串**（`nonEmpty` 返回空时 `waitStatus && ...` 短路为假，即空值不拦截）才会继续到成功返回。**两条路径下 `latestResultPayload.status` 只可能是 `"ok"` 或空**，大写化后都不等于 `"ERROR"`/`"FAILED"`——当前代码路径下无误判。但 `resultJson` 在此处是**直接透传外部 OpenClaw 网关的原始 RPC 响应**（`client.request<Record<string, unknown>>`，见 `execute.ts:1322`，无编译期类型约束、无 schema 校验），`status` 字段的实际取值范围由网关另一端的实现决定，不受本仓库代码约束。**契约层核验**：`AdapterExecutionResult.resultJson` 的类型声明（`packages/adapter-utils/src/types.ts:118`）就是裸的 `Record<string, unknown> | null`，对 `status`/`is_error` 的语义**没有任何契约层约束**——任何适配器（内置或外部）理论上都可以往这两个键塞入与"本轮回合是否失败"无关的值。**结论：现状代码路径下无误判，但存在设计风险（与判据 1 交接包里点名的"外部插件契约"同类，omp_local/antigravity_local/openclaw_gateway 是这类风险的三个实例），列为问题清单 B4（设计风险，非阻断）。**

**判据 1 结论（修正后）**：N=19，M=7，逐一核验语义（其中 6 个通过同源派生/双重独立门证明当前代码路径下无误判，1 个（openclaw_gateway）现状安全但存在外部契约风险已列入问题清单 B4），**无阻断项**。原 N=11/M=4 版本因作用面遗漏 `packages/adapters/` 下 8 个包，已在此处以完整枚举取代；结论方向不变（仍是无阻断项），但支撑证据的完整性由本次修正后的枚举提供。

### 判据 2 —— 候选取值顺序的漏判

`readStructuredFinalResponse` 遍历 `[nested, resultJson]`，返回第一个带 `status`/`is_error` 的**完整候选记录**，不跨层合并。

问题设定的场景（`resultJson.parsed.status==="SUCCESS"` 而顶层 `resultJson.is_error===true`）要求同一次运行的 `status` 与 `is_error` **分置在不同层级**。用一手源码核验了唯一已知产生 nested 形式的生产者（antigravity_local，判据1 #10）：其 `resultJson` 顶层只有 `raw`/`parsed` 两个键，从未在顶层写入 `is_error`/`status`；产生顶层展开形式的生产者（gemini_local process、claude_local process、acpx-engine，判据1 #5/#6/#9）也从未同时嵌套 `parsed` 字段。**当前已知的所有生产者里，`status`/`is_error` 要么全部在顶层，要么全部在 `resultJson.parsed` 里，从未跨层拆分。**

**结论**：这是**可接受的取舍，不是漏判**。`readStructuredFinalResponse` 把每个候选当作一份完整、互斥的记录来处理，与现实数据形状一致。风险仅存在于**未来未知的外部插件**若采用跨层拆分的写法——这是文档化不足的隐式假设，列为建议项（见问题清单 B2），不构成阻断。

### 判据 3 —— 作用域：`nativeFinalization` 分支在守卫之前

`heartbeat.ts:24290` 处 `structuredFinalFailure` 在 `nativeFinalization` 判断（`heartbeat.ts:24302`）之前计算，但 native runtime（`native-session-executor.ts`）产生的 `resultJson` 是 `{nativeResult, nativeTerminal, ...}`（判据1 #3），顶层无 `status`/`is_error`，也无 `parsed` 嵌套 → `readStructuredFinalResponse` 对该 resultJson 必返回 `null`，`structuredFinalFailure` 恒为 `null`。即便计算顺序在前，也不会影响 `nativeFinalization` 分支的判定（该分支本身不读取 `structuredFinalFailure` 变量）。

**结论**：有意的作用域划分，非遗漏。原生路径已有等价保护——`adapterResult.nativeFinalization.terminal.runTerminalState` 本身就是原生运行时自己的终态契约，是另一套独立机制。

### 判据 4 —— 正则扩面的假阳性

**① 是否命中非配额文案**：先做新旧正则对照（而非只测新正则），区分"既有行为"与"本次新增"：

```
OLD: /(?:...|quota (?:limit )?exceeded|...)/i
NEW: /(?:...|quota (?:limit )?(?:exceeded|reached)|exceeded (?:your |the )?(?:\w+ ){0,3}quota|resource[_ ]exhausted|...)/i
```

| 样本 | old | new | 备注 |
|---|---|---|---|
| `"Disk quota exceeded (os error 122)"`（POSIX EDQUOT 标准错误文案） | **true** | true | **既有行为，改动前就命中，不计入本单** |
| `"quotactl: Disk quota exceeded"` | **true** | true | 同上，既有行为 |
| `"quota reached for this billing cycle (not LLM-related)"` | false | **true** | **本次新增命中面** |
| `"You exceeded your monthly data transfer quota."` | false | **true** | **本次新增命中面** |
| `"exceeded the storage quota for this repository"` | false | **true** | **本次新增命中面** |
| `"8 RESOURCE_EXHAUSTED: bandwidth limit exceeded"` | false | **true** | **本次新增命中面** |
| `"gRPC error 8: RESOURCE_EXHAUSTED (connection pool exhausted)"` | false | **true** | **本次新增命中面** |

本次真正新增的假阳性面来自三段新词汇：`quota reached`（不带 exceeded 后缀，任意"配额"语境皆可命中）、`exceeded (?:your |the )?(?:\w+ ){0,3}quota`（"exceeded ... quota" 的宽泛 N 词模式，可命中磁盘/存储/带宽等非 LLM 配额）、`resource[_ ]exhausted`（gRPC 标准状态码字面文本，语义上不限于配额，还可能是连接池、内存等其它资源耗尽）。`classifyAdapterFailureForRecovery`（`recovery/service.ts:640`）的匹配对象是 `errorCode + error + JSON.stringify(resultJson)` 整个序列化文本，任何适配器 stdout/stderr 里偶然出现这些词汇都会被扫描到。

在本仓库当前可见的生产路径里，没有找到已知的、会在 stdout/stderr 中产出 "resource_exhausted"（非 LLM 语境）或磁盘/存储 "quota" 文案的具体调用点；这三段新增命中面目前是**理论风险**，未找到本仓库内已验证的触发实例。鉴于负责人已有的测试用例（`isProviderQuotaFailureMessage` 的反例测试）里 `"Workspace storage capacity limit reached."` 特意验证了不误判，说明负责人已意识到存储类文案的风险边界，但没有覆盖到 `"...storage quota..."`（含 quota 字面词）和 `"resource_exhausted"`（非配额语境）这两个更窄但仍可能命中的变体。

**结论**：**建议**级别（非应改、非阻断）——既有的磁盘 quota 命中问题不是本次改动引入；本次新增的三段命中面在本仓库当前已知路径中未发现实证触发点，但语义上确实比原正则更宽，建议在合并前补充这两类反例测试（"exceeded ... storage/disk quota"、非配额语境的 "RESOURCE_EXHAUSTED"），或收紧 `resource[_ ]exhausted` 为要求前后文包含 quota/429/rate 限定词。

**② 单一 owner 核验**：`heartbeat.ts:24371-24377` 的 `structuredFailureErrorFamily` 调用 `isProviderQuotaFailureMessage`（从 `recovery/service.ts` import），未在 heartbeat.ts 内另起配额正则。`grep` 全文确认 heartbeat.ts 内无 `PROVIDER_QUOTA` 或等价正则字面量。**确认是单一 owner。**

### 判据 7 —— 架构一致性

`adapter-final-response.ts` 的模式——"从 `AdapterExecutionResult.resultJson` 读取某个专用语义信号，独立成一个小模块导出一个纯函数"——在本仓库是**既有惯例**，不是新造：

- `server/src/services/acknowledged-native-stop.ts`：`hasAcknowledgedNativeStopIntent(run)` 从 `resultJson` 读取"是否已确认原生 stop 意图"这一个信号。

**结论**：不是新造模式，符合既有架构惯例，无需合并到别处。
